Show and Tell Is a Security Model

Maker Faire Orlando calls itself the Greatest Show (& Tell) on Earth. This month it filled the Central Florida Fairgrounds with robots, hackerspaces and an open-hardware recipe you can build at home. Underneath all of it ran an idea that security keeps relearning: when the design is public, more people can check it.

By Malcolm R. Smith — Savvy Security LLC · November 2026

1 · The weekend in Orlando 2 · The open thread on the floor 3 · Why open helps security 4 · Where open gets tested 5 · Safe tinkering For the technical Still open Sources

The short version

On November 6–8, 2026, Maker Faire Orlando took over the Central Florida Fairgrounds with more than 250 exhibits, a combat robot tournament, homemade electric racers and a school day that drew about 2,500 students, teachers and homeschool families (Mutti, 2026; Moeller, 2026).

Walk the exhibit list and you find the open source community everywhere: Arduino and Raspberry Pi projects, five makerspaces and hackerspaces, a ham radio club, a take-it-apart table, a tool library, and a Florida company that published its whole metal-recovery membrane as open hardware, patent license included (Maker Faire Orlando, 2026c).

That culture of showing your work is also one of the oldest ideas in security. It is how a single engineer caught the xz backdoor, how researchers proved a popular smart-card chip was broken, and how a scary “ESP32 backdoor” headline got corrected in days. It is also under pressure, from companies that close things in the name of security. The last part of this article is a plain checklist for tinkering safely.

1 · The weekend in Orlando

Maker Faire Orlando ran on Saturday and Sunday, November 7 and 8, from 10 AM to 5 PM, at the Central Florida Fairgrounds & Expo Halls on West Colonial Drive. Advance tickets were $15 for youth and students and $20 for adults. Veterans, active military and first responders got in free, and families with an EBT card paid $5 a person (Moeller, 2026; Zrallack, 2026). Local coverage billed it as the 14th annual faire (Zrallack, 2026).

The faire is produced by The Maker Effect Foundation, a nonprofit that funds maker programs in Central Florida schools, community groups and makerspaces. It runs under license from Make: Community, the company behind the original Maker Faire that started in the San Francisco Bay Area in 2006, and is funded in part by Orange County’s Arts & Cultural Affairs program (Maker Faire Orlando, 2026a). Its own roots are local. The Orlando faire grew out of the members of FamiLAB, a member-run hackerspace in Longwood founded in 2009 (Wikipedia, “FamiLAB”).

Friday was Field Trip Day. Make: reports that about 2,500 students, teachers and homeschool families filled the fairgrounds for robotics, engineering, cosplay and building (Mutti, 2026). Registration had closed because the day hit capacity (Maker Faire Orlando, 2026b).

The weekend crowd got the full show. Robot Ruckus, the combat robot tournament that has been part of the faire since 2013, put more than 100 fighting robots in the arena, from one-pound “Plastic Ants” to three-pound beetleweights, built by teams like Jupiter Robotics from Lakeland and the student builders of Ruckus Robotics (Blakeslee, 2026). There were homemade electric racers, theme park designers on stage, a Minecraft crew rebuilding theme parks block by block, and enough cosplay to fill a convention (Blakeslee, 2026; Zrallack, 2026).

None of this is new to the faire. What is worth noticing is how normal it is. A whole weekend of strangers walking up to a table and asking “how does that work?” and getting a real answer is exactly the habit that keeps open software and hardware honest. I made a similar argument about the DEF CON 34 badge, an open-source security chip you get to keep, and about the free software tools almost everything else is built on.

The security booth was a game

The Anti-Hackathon has run in Orlando since 2024. Its pitch is aimed at kids, parents and “everyday people,” and it uses realistic scenarios: messages “built to make you click before you think,” accounts that are not who they say, and strangers in online games who seem a little too friendly (Maker Faire Orlando, 2026c).

That is the right format. Most people do not lose money to clever code. They lose it to a message that rushes them. A game that lets a ten-year-old practice saying “wait, who sent this?” does more good than a slide deck.

3 · Why open helps security

The Open Source Hardware Association defines open hardware as hardware “whose design is made publicly available so that anyone can study, modify, distribute,” make and sell it, and says it “gives people the freedom to control their technology” (OSHWA, n.d.). Open source software works the same way with code. For security, the key word is study. You cannot check what you are not allowed to see.

The classic slogan is Eric Raymond’s: “given enough eyeballs, all bugs are shallow” (Raymond, 1999). It is half right. Open code can be checked by anyone. That does not mean anyone did. Three stories show both halves.

The backdoor one engineer noticed

In March 2024, Andres Freund, a developer at Microsoft, was chasing a small performance problem on a test version of Debian. SSH logins were using more processor time than they should, and a memory-checking tool was throwing errors. He kept pulling the thread and found a backdoor hidden in xz, a compression library that ships in most Linux systems. It was in versions 5.6.0 and 5.6.1, it got the highest possible severity score of 10.0, and it was tracked as CVE-2024-3094 (Wikipedia, “XZ Utils backdoor”). CISA’s alert that day said the malicious code “may allow unauthorized access to affected systems” (CISA, 2024).

The scary part is how it got there. Starting in 2021, someone using the name “Jia Tan” spent more than two years earning trust on the project, while sock-puppet accounts pressured the original, overworked maintainer to hand over more control. The backdoor landed in February 2024. It was caught before it reached the stable releases most people run (Wikipedia, “XZ Utils backdoor”).

Both halves of the slogan are in that story. Because the code was open, one curious person could take it apart and prove what it did. But for two years almost nobody was looking at a library that runs on millions of machines, and the attack worked through the people, not the code. Open made the catch possible. A person paying attention made it happen.

Open doesn’t mean someone checked. It means someone can.

The secret cipher that wasn’t safe

The other direction is older. MIFARE Classic was one of the most widely used contactless smart-card chips in the world, in transit cards and building badges, and its cipher was a trade secret. In 2008 a team at Radboud University Nijmegen reverse engineered it and showed attacks that could recover the secret key from a genuine reader in under a second, tested against real systems like London’s Oyster card and the Dutch transit card (Garcia et al., 2008). By the team’s own account, the chip’s maker went to court to stop the paper, and the judge let it be published.

Keeping the design secret did not make it strong. It just meant that the first people to study it closely were outside researchers instead of a public review before launch. I bring this one up because the faire’s exhibit list included an NFC door access build (Maker Faire Orlando, 2026c). That is a great project. It is also exactly where an old, cheap tag type can quietly become a front-door key anyone can copy.

The “backdoor” that got corrected

In March 2025, headlines warned of a “backdoor” in the ESP32, the cheap Wi-Fi and Bluetooth chip inside a huge share of maker and smart-home projects, including the IoT kit on the faire floor. The researchers had found 29 undocumented debug commands in the chip’s Bluetooth controller. Within days, Espressif said the commands were “not accessible remotely” and “cannot be triggered by Bluetooth, radio signals, or over the Internet,” that the original press release “was factually corrected to remove the ‘backdoor’ designation,” and that it would still ship a fix to remove them (Espressif, 2025). The issue was tracked as CVE-2025-27840.

The finding was real. The panic was not. A community that can read the documentation, test the claim and argue about it in public turned a scary headline into an ordinary bug fix in about a week. That is the open model working the way it is supposed to.

4 · Where open gets tested

The tension right now is that “security” is also the most common reason companies give for closing things.

Arduino. Qualcomm agreed to buy Arduino in October 2025. A month later, rewritten terms of service set off a backlash. Adafruit said the new terms included a perpetual license over what users upload and a ban on reverse engineering, and that “the changes mark a clear break from the open-hardware ethos that built the platform” (Proven, 2025). Arduino answered that the reverse-engineering ban covers only its paid cloud service, and that “anything that was open, stays open,” including the IDE, schematics, tooling and libraries (Halfacree, 2025). Both statements are on the record. What Arduino does next is the test.

Bambu Lab. In January 2025, the 3D printer maker announced an “authorization” system for printer control in beta firmware, pitched as a way to keep printer communications safe and secure. Third-party software like OrcaSlicer would have to go through Bambu’s own middleman app. Hackaday pointed out that the certificate and private key were easy to pull out of that app, and argued that this undercut the security case (Posch, 2025). In April 2026, a developer who had built a fork that worked around the middleman took it down. In his account, Bambu Lab sent a cease-and-desist letter accusing him of reverse engineering its software (Bertacchi, 2026).

Here is the question I would ask about any lock like that: who does it protect, and from whom? Real security makes it harder for a stranger to take over your machine. A lock that mainly keeps the owner from choosing their own software is a business decision wearing a security badge. Sometimes a design does both. The way to tell is to see the design, which brings us back to the point of this article.

The law is catching up. The European Union’s Cyber Resilience Act is phasing in for products with software in them sold in the EU, wherever the maker is. Its vulnerability-reporting duties for manufacturers started on September 11, 2026, and the rest applies from December 11, 2027. Foundations that support open source used in commercial products get a lighter set of duties as “stewards” (OpenSSF, n.d.; Checkmarx, 2026). Security firms’ summaries say purely volunteer, non-commercial projects are exempt (Checkmarx, 2026). If you sell a kit or a gadget, check how it applies to you against the regulation itself, not a blog post.

5 · Safe tinkering: a checklist for makers

None of this is a reason to stop building. It is a reason to build with a few habits. Most of these take five minutes.

  1. Keep passwords out of code you share. GitGuardian counted 23.8 million secrets, like passwords and API keys, leaked on public GitHub in 2024, up 25% from the year before, and found that 70% of the ones leaked in 2022 still worked (GitGuardian, 2025). Your home Wi-Fi password in a project you push to GitHub is one of those. The code below shows the easy fix.
  2. Change default passwords and keep projects off the open internet. A camera, a door controller or a sensor dashboard belongs on your home network or a guest network, not exposed to the world. If you want to reach it from outside, use a VPN instead of opening a port on your router.
  3. Don’t trust a toy lock with a real door. Many cheap NFC and RFID tags use cryptography that was broken years ago (Garcia et al., 2008). They are great for learning. For an actual lock, pick a card type with modern, published cryptography and look up current research on it first.
  4. Get tools and firmware from the project’s own release page, and check them. Many projects publish checksums or signatures next to their downloads. It takes one command to check, shown below.
  5. Update the boring parts. Board packages and libraries get security fixes too, as the ESP32 story shows. Watch the project’s advisories or release notes for the chips you use.
  6. Write it up. A build log with photos, wiring and code is how the next person learns, and how someone smarter finds the mistake you missed. Documentation is a security feature.
  7. Report security bugs privately and kindly. If you find a hole in someone’s project, look for a SECURITY.md file or a security contact before posting it in public, so the maintainer can fix it first.
  8. Back the people doing the work. The xz attack worked because one maintainer was carrying a critical project nearly alone. Join a makerspace, sponsor a maintainer, or answer a beginner’s question on a forum.

For the technical: two small habits

Keep your Wi-Fi password out of your sketch

Arduino’s own examples use a separate secrets file for this. Put your network name and password there, include it from your sketch, and tell Git never to upload it. This works for ESP32 boards in the Arduino IDE. On a Chromebook, the Git commands run in the Linux (Crostini) terminal.

// arduino_secrets.h  (stays on your computer, never committed)
#define SECRET_SSID "my-network"
#define SECRET_PASS "change-me"

// sketch.ino
#include <WiFi.h>
#include "arduino_secrets.h"

void setup() {
  WiFi.begin(SECRET_SSID, SECRET_PASS);   // the password never appears in this file
}
void loop() {}
# Tell Git to ignore the secrets file
echo "arduino_secrets.h" >> .gitignore

# Before you push, look for anything that smells like a password
git grep -nIiE "pass(word)?|api[_-]?key|secret|token" -- . ':!*.md'
# Only the #include line should come back. Anything else, move it into the secrets file.

If a password already went up to GitHub, deleting the file is not enough. It stays in the history. Change the password first, then clean up.

Check a download before you flash it

When a project publishes a checksum list (often called SHA256SUMS) and a signature next to its release files, these two commands tell you whether what you downloaded matches what the project published.

# 1. Does the file match the project's published checksum?
sha256sum -c SHA256SUMS --ignore-missing
firmware.bin: OK

# 2. Was the checksum list signed by the project's key?
gpg --verify SHA256SUMS.asc SHA256SUMS
# Look for "Good signature" from a key you got from the project's own site.

One honest limit: in the xz case, the poisoned release came from an account the project itself trusted. Checksums and signatures prove where a file came from. They cannot prove the person behind it is honest. That part takes people paying attention.
